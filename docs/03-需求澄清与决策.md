## 1. 购物车与多商品统一下单

### 已有
- 订单详情模型有 `items[]`（多行展示）；支付/定金按「整单」金额设计。
- 商品分机型/SKU；零件可作为 SKU 挂在商品体系（文档库存/换件有配件概念）。

### 缺失
- **无购物车**（接口、表、小程序页均无）。
- `CreateOrderReq` 只有单个 `skuId` + `quantity`，不能一次提交多行不同 SKU。
- 小程序确认页从详情直达，仅一件。

### 建议设计
- 增加购物车：`GET/POST/PUT/DELETE /api/cart`（或本地暂存 + 提交时带 `items[]`）。
- 下单改为：`items: [{ skuId, quantity }]`；校验库存逐行锁定。
- 零件与整机同一购物车；安装/发货规则按行或按「需安装的行」聚合（见 §2、§4）。
- 金额汇总：商品小计 + 安装费（若选）+ 运费（若选）→ 管理员可再改价后生成待付金额。

### 待确认问题
见文末 **Q1、Q2**。

## 2. 上门安装可选 + 差异化安装价

### 已有
- 安装师傅选择、档期、工单履约、验收→尾款（原规格核心）。
- 商品详情有「是否含安装」文案要求；OpenAPI 示例 tag「含上门安装」。
- `CreateOrderReq` 强制 `installDate` / `installSlot`（隐含「必须装」）。

### 缺失
- **安装非强制**（无 `needInstall` 开关）。
- **安装价公式**未定义（现规格把安装多半 bundling 进货价/服务，无独立计价表）。
- 按师傅、距离、台数计价未建模。

### 建议设计
- 订单级或行级：`needInstall: boolean`；为 false 时不选师傅、不占档期、不生成安装工单。
- 安装价独立科目 `installFee`（分），展示给客户；最终以管理员确认为准（线下付款模式下尤其重要）。
- 计价建议（可配置）：  
  - 基础上门费 + 每台加价 × 台数  
  - 距离阶梯（如 ≤10km / 10–30km / >30km）  
  - 师傅等级或技能加成（可选）  
  - 零件行默认不可装或单独「上门送装」开关  
- 补充选项：**到店自提后自行安装**、**仅送货不上门调试**。

### 待确认问题
见文末 **Q3、Q4**。

## 3. 报修：多台 + 外购设备 + 额外表单

### 已有
- 单台报修：`CreateRepairReq.assetId`；保内/保外判定；报价确认。
- 设备档案 `customer_asset` / `/api/assets`；扫码绑定。
- 小程序报修页从「我的设备」选一台。

### 缺失
- 一次报修多台（多 `assetId` 或多台临时设备）。
- **非本店购买**设备：无「手工建档」完整表单（品牌/型号/购入渠道/无 SN 等）。
- 可配置「额外表单项」机制（动态字段）。

### 建议设计
- 报修单 `items[]`：每项为已有 `assetId` **或** `externalDevice{ brand, model, sn?, buyDate?, photos[], sourceNote }`。
- 外购设备提交后写入 `customer_asset`（标记 `source=EXTERNAL`），便于后续再修。
- 动态表单：后台配置字段（文本/单选/图片/是否必填），按「报修类型」挂载；首版也可先做固定扩展字段，避免过度配置化。
- 多台可生成 **一张报修单 + 多张工单**，或 **一台一单**（影响派工与报价，见 Q5）。

### 待确认问题
见文末 **Q5、Q6**。

## 4. 发货方式可选 + 查询凭证

### 已有
- 规格侧重上门安装；**本期不做自建物流**。
- 地址簿、收货地址在下单中使用。
- 无独立「发货方式 / 运单号」字段。

### 缺失
- 发货方式枚举与按方式不同的履约字段。
- 管理端录入单号 / 司机信息；客户端查询展示。

### 建议设计（含补充选项）
| 方式 | 说明 | 查询/凭证字段建议 |
| --- | --- | --- |
| 快递 | 顺丰/德邦等 | 承运商 + **运单号** + 轨迹链接（可后接查询 API） |
| 物流/货运 | 大件专线 | 物流公司 + 单号/车牌 + 预计到达 |
| 上门送货 | 店内或师傅配送（不一定安装） | 预约时段 + 配送人/电话 |
| 上门安装（送装一体） | 与 §2 联动 | 工单号 + 师傅信息 |
| **到店自提**（建议补充） | 客户到门店取货 | 提货码 + 门店地址/电话 |
| **厂家直发**（建议补充） | 经销商代下单 | 厂家单号 + 备注 |

机器与零件可 **按行选择不同发货方式**（例如机器上门安装、零件快递）。

## 5. 订单推送管理端 + 客户联系后再付款（双支付渠道）

### 已有
- 原规格：小程序定金/尾款 **微信 JSAPI** + 后台「线下收款登记」兜底。
- 订阅消息能力在文档中，但指向客户/师傅，非「推给管理员微信」。
- **已确认**：两种付款方式都要支持（微信支付 + 线下转账）；管理员可登记线下已付。

### 缺失 / 需改写
- 不宜再假设「提交订单 = 立刻拉起支付」。更贴合诉求的是：**提交意向单 → 通知管理端 → 人工沟通/改价 → 确认应付 → 客户选择支付渠道**。
- 支付实现应按 **渠道抽象**（`payment.channel = WXPAY | OFFLINE | …`），业务状态机只认「应付单是否已结清」，不绑死某一种渠道。
- 管理端实时通知形态未定；客户端需展示「待确认 / 待付款」及联系管理员入口。

### 建议设计（渠道抽象 + 确认后再付）
```
客户提交订单/报修
  → 状态：待商家确认（PENDING_REVIEW）
  → 通知管理端（列表红点 + 可选微信/企微推送）
  → 管理员与客户沟通：改价、确认安装/发货
  → 管理员确认应付金额 → 状态：待付款（PENDING_PAYMENT）
  → 客户选择支付渠道：
        A) 小程序微信支付（JSAPI）→ 回调幂等入账
        B) 线下转账（微信/银行）→ 管理员「登记收款」+ 凭证 → 入账
  → 已付款 → 再派工/发货
```
- **架构**：`PaymentChannel` 接口 + `WxPayChannel` / `OfflinePayChannel`；应付单（payment）记录 `channel`、`status`、`out_trade_no` / 凭证图。
- **一期交付**：可以 **线下优先**（先打通 OFFLINE + 后台登记），微信支付接口与表结构预留，资质/联调就绪后再打开开关；也可以一期就上线微信——见 **Q10**。
- 定金/尾款：仍可按原规格拆两段应付单，每段各自选渠道；或一期先「一笔待付」（见 Q2）。

### 待确认问题
见文末 **Q8、Q10**（通知形态；一期是否必须上线微信支付）。

## 6. 管理端：待付款、师傅安排、安装时间等

### 已有
- 文档 FR-F*：订单看板、改派、收款登记、代客下单、客户 360 等（**Web 后台**）。
- OpenAPI 仅有少量 `/api/admin/*`；仓库 **无 Vue/后台前端工程**。
- 后端 admin 模块未实现。

### 缺失
- 完整后台 UI；与用户描述的「待付款项、师傅安排、安装时间」操作台。
- 线下收款登记、改价、确认发货方式/运单号的具体界面。

### 建议设计
- **优先 Web 管理后台**（与原规格一致，表格/筛选更合适）；师傅仍用小程序。
- 若短期只要店长手机处理：可做「管理员角色小程序页」做轻量看板，但复杂改价/对账仍建议 Web。
- MVP 后台能力清单建议：  
  1）新订单/报修列表与详情  
  2）改价 / 确认应付  
  3）登记线下收款（及查看微信支付到账）  
  4）选择发货方式并填单号  
  5）派师傅 / 改安装时间  
  6）客户微信/手机一键复制或跳转  

### 待确认问题
见文末 **Q8、Q9**。

## 对原规格的修订建议（拍板后可改文档）

1. **支付**：保留微信 JSAPI，同时强化线下登记；统一为支付渠道抽象；流程上增加「商家确认应付」后再打开支付入口（渠道可选）。  
2. **下单模型**：单 SKU → 购物车 / `items[]`。  
3. **安装**：必选 → 可选 + 独立安装费。  
4. **履约**：增加发货方式与物流凭证。  
5. **报修**：单台本店设备 → 多台 + 外购设备建档。  
6. **状态机**：增加「待商家确认」等态；「已付款」可由微信回调或管理员登记触发。
