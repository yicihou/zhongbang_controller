## 一、技术选型

### 1.1 选型原则

1. **一个人能看懂、能维护**：优先选择主流、文档多、社区活跃的技术，不引入团队没接触过的组件；
2. **单体优先**：业务量（日订单 50–200 单）远未到需要微服务的地步，单体 + 模块化分包即可，未来按需拆分；
3. **托管优先**：能用云服务（对象存储、短信、RDS）就不自己运维；
4. **钱要能算清**：支付、金额、对账相关的实现必须简单、可审计，不炫技。

### 1.2 技术栈

| 层次 | 选型 | 版本 | 选择理由 |
| --- | --- | --- | --- |
| 小程序 | 微信原生框架 + TDesign Miniprogram | 基础库 2.30+ | 无跨端需求，原生性能最好，组件库成熟 |
| 管理后台 | Vue 3 + Vite + Element Plus | — | 生态成熟、表格表单组件完善、上手快 |
| 后端框架 | Spring Boot | 3.2.x | 事实标准，资料最多 |
| JDK | OpenJDK | 17 | Spring Boot 3 最低要求，长期支持 |
| 持久层 | MyBatis-Plus | 3.5.x | 比 JPA 更贴近 SQL，便于排查慢查询 |
| 数据库 | MySQL | 8.0 | 事务、窗口函数、JSON 字段够用 |
| 缓存/锁 | Redis | 7.x | 会话、库存预占、档期锁、验证码 |
| 消息队列 | RabbitMQ | 3.12 | 延迟队列实现"30 分钟未支付自动关单" |
| 对象存储 | 阿里云 OSS / MinIO | — | 图片视频直传，CDN 加速 |
| 鉴权 | Spring Security + JWT | — | 无状态、小程序友好 |
| 微信 SDK | WxJava（weixin-java-miniapp / pay） | 4.6.x | 封装登录、订阅消息、支付 v3 |
| 接口文档 | SpringDoc + Knife4j | — | 自动生成，前后端联调效率高 |
| 定时任务 | Spring `@Scheduled` + ShedLock | — | 单机够用；多实例时用 ShedLock 防重复执行 |
| 部署 | Docker Compose + Nginx | — | 一台 2C4G 服务器即可跑完整环境 |
| 监控 | Spring Boot Actuator + Prometheus + Grafana | — | 指标可视化，异常告警 |
| 日志 | Logback + Loki（或 ELK） | — | traceId 贯穿，按订单号检索 |

## 四、关键设计

### 4.1 登录与会话

```
小程序                后端                         微信
  │  wx.login → code   │                            │
  ├───────────────────▶│ POST /api/auth/login       │
  │                    ├── jscode2session ─────────▶│
  │                    │◀── openid / session_key ───┤
  │                    │ 查 customer(openid)         │
  │                    │ 不存在则建档（游客态）        │
  │                    │ 签发 JWT(30 天) + refresh   │
  │◀── token ──────────┤                            │
  │                    │                            │
  │  手机号授权按钮      │                            │
  ├───────────────────▶│ POST /api/auth/phone       │
  │  (code)            ├── 换取手机号（或解密）──────▶│
  │                    │ 按手机号合并客户档案         │
  │◀── 更新 token ─────┤                            │
```

要点：

- 小程序端把 token 存 `wx.setStorageSync`，请求拦截器统一加 `Authorization: Bearer xxx`；
- token 过期返回 401，前端静默重新 `wx.login` 换新 token，用户无感；
- **手机号是客户唯一业务标识**：老客户换微信号，输入同一手机号应看到历史订单，因此合并逻辑按手机号执行（BR-12）；
- 员工端（后台）与师傅端复用同一套 JWT，但 `subject` 类型不同（`CUSTOMER` / `STAFF` / `TECHNICIAN`），鉴权时校验类型，防止客户 token 调用后台接口。

### 4.2 订单号与幂等

- **主键**：雪花 ID（`bigint`），避免自增暴露单量，也便于未来分库；
- **业务单号**：`SO` + `yyyyMMdd` + 6 位日序列（Redis `INCR`，当天过期），如 `SO20251123000123`；
- **支付单号**：订单号 + `-D`（定金）/ `-B`（尾款）/ `-R`（维修费），作为微信 `out_trade_no`，天然幂等；
- **接口幂等**：下单接口要求前端传 `requestId`（UUID），后端用 Redis `SETNX requestId` 10 分钟，重复请求直接返回上次结果，防止用户连点生成两笔订单。

### 4.3 订单状态机

状态枚举与允许的迁移集中定义，任何状态变更都走同一个入口，并落 `order_status_log`。

```java
public enum OrderStatus {
    UNPAID,          // 待付款
    DEPOSIT_PAID,    // 已付定金 / 待安装
    INSTALLING,      // 安装中
    PENDING_BALANCE, // 待付尾款
    COMPLETED,       // 已完成
    CANCELLED,       // 已取消
    REFUNDING,       // 退款中
    REFUNDED         // 已退款
}

public final class OrderStateMachine {
    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
        UNPAID,          Set.of(DEPOSIT_PAID, CANCELLED),
        DEPOSIT_PAID,    Set.of(INSTALLING, REFUNDING, CANCELLED),
        INSTALLING,      Set.of(PENDING_BALANCE, REFUNDING),
        PENDING_BALANCE, Set.of(COMPLETED, REFUNDING),
        REFUNDING,       Set.of(REFUNDED, DEPOSIT_PAID)
    );

    /** 唯一的合法变更入口：校验 + CAS 更新 + 写日志 */
    @Transactional
    public void transfer(Order order, OrderStatus target, String operator, String remark) {
        if (!ALLOWED.getOrDefault(order.getStatus(), Set.of()).contains(target)) {
            throw new BizException(ErrorCode.ILLEGAL_STATE,
                "订单 " + order.getOrderNo() + " 不允许从 " + order.getStatus() + " 变更为 " + target);
        }
        int n = orderMapper.casUpdateStatus(order.getId(), order.getStatus(), target);
        if (n == 0) throw new BizException(ErrorCode.CONCURRENT_MODIFIED, "订单状态已变化，请刷新");
        statusLogMapper.insert(OrderStatusLog.of(order.getId(), target, operator, remark));
    }
}
```

`casUpdateStatus` 的 SQL 带原状态条件：`UPDATE orders SET status=#{target} WHERE id=#{id} AND status=#{from}`。这样即使支付回调和人工取消同时发生，也只有一个能成功，从根上避免"已取消订单被改成已支付"。

### 4.4 支付与回调

**支付流程（定金为例）**

| 步骤 | 参与方 | 动作 | 关键点 |
| --- | --- | --- | --- |
| 1 | 小程序 | `POST /api/pay/prepay {orderId, type:DEPOSIT}` | 金额由服务端计算，前端只传订单号 |
| 2 | 后端 | 校验订单状态与金额，创建 `payment` 记录（WAIT） | 同一订单同类型未决支付单只允许一条 |
| 3 | 后端 | 调微信 v3 JSAPI 下单，`out_trade_no = 订单号-D` | 金额单位"分" |
| 4 | 后端 | 返回 `prepay_id` 及签名参数 | 签名由 SDK 生成，禁止前端参与 |
| 5 | 小程序 | `wx.requestPayment(...)` | 前端结果仅用于 UI 提示 |
| 6 | 微信 | 异步通知 `POST /api/pay/notify` | **订单状态的唯一可信来源** |
| 7 | 后端 | 验签 → 解密 → 幂等校验 → 更新支付单/订单 → 发 MQ | 幂等键：`out_trade_no` 唯一索引 |
| 8 | 后端 | 返回 `{"code":"SUCCESS"}` | 非 200 或非成功应答，微信会重试 |

**回调幂等的实现**（这是最容易出错的地方）：

```java
@Transactional
public void handleNotify(String body, String serial, String signature, String timestamp, String nonce) {
    // 1. 验签（平台证书）+ 解密（AEAD_AES_256_GCM）
    WxPayNotify notify = wxPayAdapter.parseAndVerify(body, serial, signature, timestamp, nonce);
    // 2. 幂等：payment 表 out_trade_no 唯一索引，状态非 WAIT 直接返回成功
    Payment pay = paymentMapper.selectByOutTradeNo(notify.getOutTradeNo());
    if (pay == null) { log.error("未知支付单 {}", notify.getOutTradeNo()); return; }
    if (pay.getStatus() == PayStatus.SUCCESS) return;              // 已处理
    // 3. CAS 置为成功，失败说明并发，直接返回
    if (paymentMapper.markSuccess(pay.getId(), notify.getTransactionId(),
            notify.getSuccessTime()) == 0) return;
    // 4. 按类型推进订单状态（内部走状态机）
    orderService.onPaid(pay);
    // 5. 异步：生成工单 / 发订阅消息 / 推送师傅
    rabbitTemplate.convertAndSend("pay.success", pay.getId());
}
```

**兜底机制**：

- **主动查单**：每 5 分钟扫描 `status=WAIT` 且创建超过 2 分钟的支付单，调微信查单接口补齐状态；
- **每日对账**：T+1 下载微信账单，与 `payment` 表逐笔比对，差异写入 `recon_diff` 表并告警；
- **退款**：走 v3 退款接口，退款单独立建表，回调同样幂等处理。

### 4.5 派单与档期

**派单规则（按优先级）**

1. 客户指定了师傅 → 校验技能与档期 → 直接指派（30 分钟未接则改派）；
2. 未指定 → 按综合分排序取前 3 名推送抢单，30 分钟无人接则依次降级；
3. 仍无 → 转人工，进入"待派单"看板并提醒店长。

**综合分** = 距离分（40%）+ 技能匹配（25%）+ 评分（20%）+ 当前负载（15%）。距离用客户地址与师傅服务区域的经纬度直线距离，超过 30 公里直接排除。

**档期防并发**：师傅某日容量用 Redis 计数 + 数据库唯一约束双保险。

```
-- 档期占用表：一人一天一段，唯一索引兜底
UNIQUE KEY uk_tech_date_slot (technician_id, service_date, time_slot)
```

下单时先 `INCR technician:{id}:{date}` 判断是否超容量，落库失败则回滚计数。宁可让用户重选一次，也不能出现两个客户同时约到同一位师傅的同一时段。

### 4.6 库存扣减

三段式，避免超卖又不长时间锁行：

| 阶段 | 动作 | 存储 |
| --- | --- | --- |
| 下单 | 预占 +N（Redis 计数），校验 `可用 = 库存 − 锁定 > 0` | Redis |
| 支付成功 | 数据库 `stock = stock - N`，`locked = locked - N` | MySQL（乐观锁 `version`） |
| 取消/超时 | 释放预占，`locked = locked - N` | Redis + MySQL |

数据库层面保留 `stock`（实物）、`locked`（已售未发/未装）、`available`（计算列或视图），库存流水表记录每一笔变化，便于盘点对账。

### 4.7 消息通知

订阅消息是微信小程序唯一的主动触达渠道，且**一次性订阅需要用户每次授权**，因此设计上要克制：

| 模板 | 触发时机 | 订阅时机（向用户要授权） |
| --- | --- | --- |
| 订单支付成功 | 支付回调后 | 提交订单页 |
| 师傅已接单/预约上门 | 派单成功 | 支付成功页 |
| 上门提醒 | 上门前 2 小时 | 支付成功页 |
| 尾款待支付 | 验收后 | 验收页 |
| 维修进度更新 | 工单状态变更 | 报修提交页 |
| 保修即将到期 | 到期前 30 天 | 我的设备页 |

实现上抽一层 `NoticeService.send(templateCode, openid, params)`，内部记录 `notice_log`（含微信返回的 errcode），失败进入重试队列。**关键提醒：一次性订阅一条只能发一条，重要节点（尾款、上门）要在多个触点重复引导授权。**

### 4.8 文件上传

小程序直传 OSS，后端只发签名，不中转文件（省带宽、省内存）：

```
1. 小程序 GET /api/file/policy?bizType=WORKORDER_PHOTO
2. 后端返回 OSS 临时签名（policy + signature + key 前缀）
3. 小程序 wx.uploadFile 直传 OSS
4. 上传成功后把 objectKey 回传业务接口（如工单提交）
5. 展示时后端生成带时效的签名 URL（私有读）
```

图片在前端压缩到 1080px、视频限制 30 秒 / 20MB，否则师傅在工地弱网下上传会失败——这是实际落地最常见的坑。

### 4.9 多租户与多门店预留

当前按单店设计，但所有业务表预留两个字段，未来 SaaS 化时不需要大改：

- `tenant_id`（经销商/租户）：MyBatis-Plus `TenantLineHandler` 自动拼接，业务代码无感；
- `store_id`（门店）：用于多门店库存、业绩归属、数据权限。

第一版把 `tenant_id` 固定为 1，`store_id` 允许为空（单店时为空表示总店）。

### 5.4 索引与查询要点

- 订单列表按 `(tenant_id, status, created_at)` 走索引，避免全表扫描；
- 客户 360 页需要聚合查询，**不要在请求时实时 join 十几张表**：订单汇总、设备数、待付金额用定时任务每 10 分钟预聚合到 `customer_stat` 表（或用 Redis Hash 缓存），详情页只查两张表；
- 报表类查询走只读从库（若配置了主从），避免拖慢交易链路；
- 大字段（图片、签字）只存 objectKey，不存二进制。

### 6.1 规范

| 项 | 约定 |
| --- | --- |
| 风格 | REST，`/api/{module}/{resource}`；后台接口统一 `/api/admin/**` |

### 7.2 请求封装

```javascript
// utils/request.js
const BASE = 'https://api.example.com';
let refreshing = null;

function request(options) {
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE + options.url,
      method: options.method || 'GET',
      data: options.data,
      header: { Authorization: `Bearer ${wx.getStorageSync('token')}` },
      success: async (res) => {
        if (res.statusCode === 401) {            // token 过期：静默续期
          refreshing = refreshing || login();
          await refreshing; refreshing = null;
          return resolve(request(options));       // 重放一次
        }
        if (res.data.code !== 0) {
          if (res.data.code !== 4001) wx.showToast({ title: res.data.msg, icon: 'none' });
          return reject(res.data);
        }
        resolve(res.data.data);
      },
      fail: reject
    });
  });
}
```

## 八、安全与合规

| 风险 | 措施 |
| --- | --- |
| 金额篡改 | 金额一律服务端按 SKU 与规则计算，前端传的金额仅作校验比对 |
| 越权访问 | 每次查询强制带 `customer_id`/`technician_id` 条件；后台用 `@DataScope` 限制 |
| 支付回调伪造 | 平台证书验签 + 解密 AES-GCM + 时间戳 5 分钟内有效 |
| 重放攻击 | 业务接口带 `requestId` 幂等；回调靠唯一索引 |
| SQL 注入 | MyBatis 全部 `#{}`，禁止 `${}` 拼接（排序字段用白名单） |
| 敏感数据 | 手机号在日志中脱敏（`138****8000`），身份证/银行卡不落库 |
| 文件安全 | 私有读 + 签名 URL（10 分钟有效），禁止直链传播 |
| 账号安全 | 后台强密码 + 登录失败锁定 + 操作日志 |
| 个人信息合规 | 隐私政策、授权弹窗、最小必要、可注销、可导出 |
| 数据备份 | 每日全备 + binlog 增量，异地存储，季度恢复演练 |

## 十二、演进路线

| 阶段 | 目标 | 关键改动 |
| --- | --- | --- |
| V1（本期） | 单店闭环 | 单体 + 单租户（tenant_id=1） |
| V1.5 | 多门店 | 启用 `store_id`，库存与业绩按门店归属，数据权限下沉 |
| V2 | 多经销商 SaaS | 启用多租户、独立商户号与分账、按租户计费；应用仍可单体，按租户分库或加 `tenant_id` 隔离 |
| V2.5 | 服务网络 | 师傅抢单大厅、跨区域派单、师傅评价体系 |
| V3 | 数据与智能 | 故障知识库、AI 故障自诊、备件需求预测、客户流失预警 |
| V3.5 | 产业协同 | 与厂商 ERP 对接（整机 SN 溯源、保修互认）、供应链采购 |

> 演进的基本原则：**先把一条链跑通、跑顺、跑出数据**。多商户、分账、AI 这些能力，等单店模型验证过再投入，否则很容易做成"功能齐全但没人用"的系统。
