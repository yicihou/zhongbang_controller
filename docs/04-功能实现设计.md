## 1. 目标与一期边界

### 1.1 业务目标
- 客户可把整机与零件加入购物车，一次下单统一付款。
- 订单行可选发货方式；仅「上门安装」产生安装费（按行，管理员定价）。
- 报修支持一单多行（含外购设备）。
- 提交后按标价生成待付；管理员可改价；一期线下收款登记；微信支付渠道预留。
- Web 管理后台优先；新单实时推送；管理端小程序建议二期或并行轻量版。

### 1.2 一期（Phase 1）范围
| 做 | 不做 / 后做 |
| --- | --- |
| 购物车 + 多行下单 | 微信支付实付（仅预留 channel=WXPAY） |
| 五行发货 + 运单/凭证字段 | 快递轨迹第三方实时查询 API |
| 上门安装行安装费（管理员改） | 自动距离/师傅公式计价引擎 |
| 报修一单多行 + 外购设备 | 动态表单配置中心（先用固定扩展字段） |
| 线下支付登记 + 应付单 | 微信支付实付 |
| 管理员手加运费 / 手拆定金+尾款（默认可一笔） | 自动定金比例引擎 |
| Web 后台：订单/报修/改价/收款/派工/发货 | 完整企微；管理端小程序可二期 |
| 管理端实时推送：SSE/WebSocket | 服务号/企微推送（二期） |

### 1.3 二期及以后
- 打开 `WXPAY`：JSAPI 预下单、回调、查单补偿。
- 管理端小程序（看板 + 改价 + 登记收款 + 派工）。
- 企微/服务号模板推送；快递轨迹对接。
- 可选：厂家直发、安装费公式。

## 2. 领域模型与表设计（Flyway）

在现有 `V1__init.sql`（customer / product / orders 等）之上增量迁移，例如 `V2__cart_fulfillment_repair_payment.sql`。下列为逻辑模型；命名可与现表合并演进（`orders` 已存在则 ALTER）。

### 2.1 枚举

| 枚举 | 值 |
| --- | --- |
| `DeliveryMethod` | `EXPRESS` 快递 / `FREIGHT` 物流货运 / `HOME_DELIVERY` 上门送货 / `ON_SITE_INSTALL` 上门安装 / `STORE_PICKUP` 到店自提 |
| `PaymentChannel` | `OFFLINE` / `WXPAY`（预留） |
| `PaymentStatus` | `WAIT` / `SUCCESS` / `CLOSED` / `REFUNDED` |
| `PaymentType` | `FULL`（默认全款）/ `DEPOSIT` / `BALANCE` / `REPAIR` / `FREIGHT`（可选，运费也可并入 FULL 的金额字段） |
| `OrderStatus` | 见 §3.1 |
| `RepairStatus` | 见 §3.2 |
| `AssetSource` | `INTERNAL` 本店售出 / `EXTERNAL` 外购 |

### 2.2 购物车

```text
cart_item
  id, tenant_id, customer_id, sku_id, quantity
  delivery_method          -- 可在加购时默认，确认页可改
  need_install             -- 冗余：当 delivery_method=ON_SITE_INSTALL 时为 true
  created_at, updated_at
  UNIQUE(customer_id, sku_id)  -- 同 SKU 合并数量；若同 SKU 要不同发货方式则改为无唯一、按行 id 改
```

> 实现建议：若业务上「同 SKU 不同发货」少见，用 `UNIQUE(customer_id, sku_id, delivery_method)`。

### 2.3 订单与订单行（改价、发货、安装费）

```text
orders（扩展）
  id, tenant_id, order_no, customer_id, store_id
  status
  goods_amount             -- 商品标价合计（分）；下单时写入
  install_amount           -- 安装费合计（管理员可改）
  freight_amount           -- 运费合计；**默认 0，仅管理员手加**（D11）
  adjust_amount            -- 其它改价调整额（可正可负）
  payable_amount           -- 订单应付总额 = goods + install + freight + adjust（展示用）
  paid_amount              -- 已入账 payment 合计
  contact_remark           -- 客户备注
  admin_remark
  price_adjusted           -- bool，是否改过价
  created_at, updated_at, deleted

order_item
  id, order_id, sku_id, product_name, sku_name, cover_image
  quantity, unit_price, line_amount
  delivery_method
  install_fee              -- 仅 ON_SITE_INSTALL 可 >0；管理员可改
  install_date, install_slot, technician_id   -- 仅上门安装行有意义
  address_snapshot_json    -- 或订单级地址 + 行覆盖
  shipment_id              -- 可空，发货后关联
```

地址：订单级默认收货地址；自提行可存 `pickup_store_id`。

### 2.4 发货 / 履约凭证

按「发货单」聚合相同方式+相同地址的行，或一行一单（一期推荐 **一行一 shipment**，简单）。

```text
shipment
  id, order_id, order_item_id
  method                   -- DeliveryMethod
  status                   -- PENDING / DISPATCHED / DONE / CANCELLED
  -- EXPRESS
  carrier, tracking_no
  -- FREIGHT
  logistics_company, freight_no, vehicle_no
  -- HOME_DELIVERY / ON_SITE_INSTALL
  courier_name, courier_mobile, appoint_at
  -- STORE_PICKUP
  pickup_code, pickup_store_id, picked_at
  remark, created_at, updated_at
```

客户查询：按 method 返回对应字段；快递展示 `carrier + tracking_no`。

### 2.5 安装 / 师傅排班

沿用并扩展原 `work_order` / `technician` / `technician_schedule`：

- 仅 `delivery_method=ON_SITE_INSTALL` 的行生成 `work_order`（type=INSTALL），关联 `order_item_id`。~~须已付款（或管理员允许预派）~~ → **变更（2026-11-24，D12）**：不要求已付款，订单未取消即可派工。
- `technician_schedule`：`technician_id, service_date, time_slot, capacity, used` + 唯一约束防超卖。
- 安装费不在排班表；在 `order_item.install_fee`。

### 2.6 报修（一单多行 + 外购）

```text
repair_ticket
  id, tenant_id, ticket_no, customer_id
  status
  expect_date, expect_slot
  contact_mobile, remark
  quote_amount, payable_amount, paid_amount
  created_at, updated_at

repair_line
  id, ticket_id, line_no
  asset_id                 -- 可空（外购新建前）
  -- 外购/展示快照
  brand, model, sn
  source                   -- INTERNAL / EXTERNAL
  fault_type, fault_desc
  images_json              -- 必填至少 1
  purchase_proof_url       -- 选填
  purchase_channel         -- 选填
  line_quote_amount
  work_order_id            -- 派工后

customer_asset（扩展）
  source, brand            -- EXTERNAL 时可无 sku_id
```

规则：提交外购行时同步插入/更新 `customer_asset(source=EXTERNAL)`，便于下次再选。

### 2.7 支付（渠道抽象）

```text
payment
  id, tenant_id
  biz_type                 -- ORDER / REPAIR
  biz_id                   -- orders.id / repair_ticket.id
  payment_no               -- 内部单号
  out_trade_no             -- 微信用；线下可空或同 payment_no
  channel                  -- OFFLINE / WXPAY
  type                     -- FULL / DEPOSIT / BALANCE / REPAIR / …
  title                    -- 展示名，如「全款」「定金」「尾款」「运费补收」
  amount
  status                   -- WAIT / SUCCESS / CLOSED / REFUNDED
  sort_no                  -- 同订单多笔时的顺序
  transaction_id           -- 微信
  voucher_urls_json        -- 线下凭证
  offline_method           -- 线下收款方式：BANK_TRANSFER / WECHAT_TRANSFER / ALIPAY / CASH / OTHER（2026-11-24 增）
  paid_at, operator_id     -- 线下登记操作员
  split_from_id            -- 部分收款时拆出的剩余待付指向原应付（2026-11-24 增）
  created_at, updated_at
  UNIQUE(out_trade_no)
```

- **下单成功（D2/D10）**：默认生成 **一笔** `payment(type=FULL, status=WAIT, amount=goods+install)`；`freight_amount=0`，运费不自动进应付。
- **管理员可**：
  - `adjust-price` / 设置 `freight_amount`（D11）后，把差额并入未付 FULL，或另建一笔 WAIT payment；
  - **拆阶段**：取消/关闭原 FULL（仅 WAIT），改为手动创建 `DEPOSIT` + `BALANCE`（金额由管理员填，不强制 30%）；
  - 随时 **追加** 一笔 WAIT（如补运费、补尾款）。
- 订单 `PAID` 条件：所有关联 WAIT 已结清，或业务规则定义为「当前应付合计已付清」（见状态机）。
- 改价：仅更新仍为 WAIT 的 payment；已 SUCCESS 走 O1。
- 线下：`POST /api/admin/payments/{id}/offline-confirm`。
  - **变更（2026-11-24，用户决定）：支持部分收款。** 请求体 `{ amount, method, paidAt, voucherUrls?, remark? }`。`amount` 为本次实收（分），须 > 0 且 ≤ 该笔 WAIT 金额，不传按全额；`method` 必填，取 `BANK_TRANSFER / WECHAT_TRANSFER / ALIPAY / CASH / OTHER`；`paidAt` 为 `yyyy-MM-dd HH:mm:ss`，不能晚于当前时间，不传取服务器时间。凭证改为选填。
  - `amount` 小于该笔金额时：原 payment 的 `amount` 改为实收金额并记 `SUCCESS`；剩余部分新建一笔 `WAIT`（同 `type`、`channel=OFFLINE`，标题加「（余款）」，`split_from_id` 指向原笔，`sort_no` 取最大 +1）。未关闭 payment 合计仍等于订单应付，改价/运费逻辑不受影响。
  - 订单状态随之按 §3.1 推导：仍有 WAIT 且已付 > 0 → `PARTIALLY_PAID`；全部结清 → `PAID`（或按履约进度 `FULFILLING` / `COMPLETED`）。报修单仍有 WAIT 时保持 `PENDING_PAYMENT`。
- 微信（二期）：对某一笔 WAIT 调 `prepay` + `/api/pay/notify`。

### 2.8 管理端推送收件箱（可选轻表）

```text
admin_notice
  id, tenant_id, user_id, title, body, biz_type, biz_id, read_flag, created_at
```

SSE/WebSocket 推送同时落库，刷新可拉未读。

## 3. 状态机

### 3.1 销售订单 `OrderStatus`

```text
PENDING_PAYMENT   -- 已提交，至少有一笔 WAIT 应付（默认 FULL=标价）；可改价/加运费/拆定金尾款
PARTIALLY_PAID    -- 可选：多笔中部分 SUCCESS（一期可用 paid_amount vs 应付合计表达，不一定单独成态）
PAID              -- 当前所有 WAIT 已结清（或无 WAIT 且已付合计覆盖订单应付）
FULFILLING        -- 发货/安装进行中（可细分为按行）
COMPLETED         -- 全部履约完成
CANCELLED
```

合法迁移（一期简化）：

| From | To | 触发 |
| --- | --- | --- |
| PENDING_PAYMENT | PAID | 全部 WAIT 线下登记成功 / 未来微信回调 |
| PENDING_PAYMENT | PENDING_PAYMENT | 管理员加运费、拆 DEPOSIT/BALANCE、改 WAIT 金额（仍待付） |
| PENDING_PAYMENT | CANCELLED | 客户或管理员取消（无成功付款） |
| PAID | FULFILLING | 首次发货或生成安装工单 |
| PAID / FULFILLING | PENDING_PAYMENT | 管理员追加新的 WAIT（补运费/补尾款）且未付清 |
| FULFILLING | COMPLETED | 所有 shipment/工单完成 |
| PAID / FULFILLING | CANCELLED | 仅退款流程（二期） |

说明：原规格「待安装 / 待尾款」等可映射为 `FULFILLING` + 多笔 `payment(type=BALANCE)`，不必单独订单态。  
**D2/D10/D11**：进入 `PENDING_PAYMENT` 时默认一笔 FULL；运费默认 0；定金/尾款/运费均由管理员在后台手加或拆分。

改价 / 拆阶段约束：优先改 `status=WAIT` 的 payment；已 SUCCESS 见 O1。

**变更（2026-11-24，用户决定，D12）：先发货后收款。** 收款与履约是两条独立进度，订单状态只用一个字段，按下列优先级推导：

1. `CANCELLED` / `COMPLETED` 为终态，不再变化；这两种状态下不能发货、派工。
2. 仍有 WAIT 应付：已付为 0 → `PENDING_PAYMENT`，已付 > 0 → `PARTIALLY_PAID`。**即使已有行发货，也保持待付款 / 部分付款**；发货进度看各行的 `shipment`（管理端另显示「已发货 n/m 行」）。
3. 无 WAIT 且已付覆盖应付：所有行的 `shipment.status=DONE` → `COMPLETED`；有任一行已发出或已派工 → `FULFILLING`；否则 `PAID`。

由此补充的迁移：

| From | To | 触发 |
| --- | --- | --- |
| PENDING_PAYMENT / PARTIALLY_PAID | （不变） | 未付清时按行发货 / 派上门安装师傅 |
| PENDING_PAYMENT / PARTIALLY_PAID | FULFILLING | 已有行发货，最后一笔 WAIT 线下登记 |
| PENDING_PAYMENT / PARTIALLY_PAID | COMPLETED | 全部行已完成，最后一笔 WAIT 线下登记 |

约束：同一行已有未取消的 shipment 时不能重复发货；已有发货或派工记录的订单不能直接取消（需先处理退货/撤派，退款流程二期）。上表中 `PAID → FULFILLING` 一行不再是发货的前置条件。

### 3.2 报修单 `RepairStatus`

```text
SUBMITTED         -- 已提交，推送管理端
QUOTED            -- 管理员已报价（可改）
PENDING_PAYMENT   -- 有应付（保外）；保内可跳过
PAID / CONFIRMED  -- 已付或保内确认可派工
IN_SERVICE        -- 已派工
DONE
CANCELLED
```

| From | To | 触发 |
| --- | --- | --- |
| SUBMITTED | QUOTED | 管理员报价 |
| QUOTED | PENDING_PAYMENT | 保外且金额>0 |
| QUOTED | CONFIRMED | 保内或 0 元 |
| PENDING_PAYMENT | PAID | 线下/微信 |
| PAID / CONFIRMED | IN_SERVICE | 派工 |
| IN_SERVICE | DONE | 全部行完工 |
| * | CANCELLED | 规则内取消 |

多行：票级状态由行聚合；派工可按行生成多个 `work_order`。

## 5. 管理端实时推送

### 5.1 一期推荐
- **SSE**（`GET /api/admin/stream`，JWT 或 ticket）：事件类型 `ORDER_CREATED` / `REPAIR_CREATED` / `PAYMENT_OFFLINE_PENDING` 等。
- 服务端在下单/报修提交后：写 `admin_notice` + 向在线 SSE 连接推送。
- Web 后台：`EventSource` 收事件 → Toast + 列表刷新。
- 优点：实现简单、经 Nginx 可反代；足够「实时」。

备选：WebSocket（若需双向）；一期二选一即可，推荐 SSE。

### 5.2 二期增强
- 微信小程序 **订阅消息**（管理员账号也走小程序）或 **企业微信** 应用消息。
- 配置项：`zhongbang.notify.channels = [SSE, WX_SUBSCRIBE, WECOM]`。

### 5.3 降级
- SSE 断开时轮询 `GET /api/admin/notices?unread=1`（30s）。

## 6. 关键流程（一期）

### 6.1 下单付款发货
```
加购 → 确认页选每行发货方式（上门安装则填档期/师傅，install_fee 先 0 或后台默认估值）
  → POST /api/orders（算 goods_amount；install 仅 ON_SITE_INSTALL 行；freight=0）
  → 默认一笔 payment(FULL,WAIT) + 订单 PENDING_PAYMENT
  → SSE 通知管理员
  → 客户与管理员微信沟通；管理员可 adjust-price / 设运费 / 拆定金·尾款
  → 客户按 WAIT 笔线下转账；管理员逐笔 offline-confirm → 全部结清则 PAID
  → 管理员录入 shipment / 派安装工单 → FULFILLING → COMPLETED
```
> **变更（2026-11-24，用户决定，D12）**：「结清 → 再录 shipment / 派工」不再是顺序要求。PENDING_PAYMENT / PARTIALLY_PAID 时即可按行录入 shipment（单号/凭证）、派安装工单，订单状态仍显示待付款 / 部分付款；之后逐笔 offline-confirm，结清时按履约进度直接进入 FULFILLING 或 COMPLETED（规则见 §3.1）。

### 6.2 报修
```
选择多台设备或填写外购信息 → POST /api/repairs
  → SSE 通知 → 管理员报价 → 客户确认
  → 保外：payment WAIT → 线下登记 → 派工
  → 保内：直接派工 → 完工
```
