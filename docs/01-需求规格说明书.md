## 一、项目概述

### 1.1 项目背景

缝纫机经销是一个"高客单价、重服务、强关系"的行业。一台家用多功能机 1,000–5,000 元，工业平缝机 3,000–15,000 元，特种机（绣花机、模板机、包缝机）动辄数万元；成交之后还必须上门安装、调机、试缝、培训，后续还有保修、维修、换件、以旧换新。目前多数经销商的实际作业方式是这样的：

- **接单靠微信聊天**：客户在微信里发型号、砍价、发地址，店员手工记录，漏单、错单、报价不一致时有发生；
- **台账靠 Excel 或手写本**：订单、定金、尾款分散在多个表格，月底对账要翻聊天记录；
- **师傅调度靠电话**：谁有空、谁擅长哪种机型、客户指定的师傅今天在哪，全凭店长脑子；
- **尾款靠记忆催收**：安装完了忘了收尾款，或者客户拖两三个月，应收账款越滚越大；
- **报修无留痕**：客户说"上次没修好"，店里拿不出照片、报价单和签字记录，容易扯皮；
- **客户资产不沉淀**：老客户买过什么机器、偏好哪个品牌、家里有几台设备、保修什么时候到期，全散落在各人微信里，复购和转介绍做不起来。

这些问题的共同点是：**交易过程没有被结构化记录**。一个小程序 + 一个后台，把"下单—收款—派工—安装—报修—回访"这条链路固化下来，收益是直接的：少漏单、快回款、可追责、能复购。

### 1.2 产品定位

一套面向**单经销商（含其下属门店）**的微信小程序 + 商家管理后台，覆盖"卖机器"和"修机器"两条主线：

- **客户端（微信小程序）**：看机型、选配置、下单、指定安装师傅、付定金、跟踪进度、付尾款、报修、选维修师傅、评价。
- **师傅端（同一小程序，按角色切换）**：接单、改约、导航打卡、上传安装/维修单、客户签字。
- **商家端（Web 后台）**：客户 360 档案、订单全流程、已付/待付/逾期账款、师傅排班与派单、库存、保修规则、报表。

产品不追求做成"行业电商平台"，而是先解决一个经销商自己的经营闭环；架构上预留多商户能力，跑通后再考虑 SaaS 化（见架构文档 §12）。

### 1.3 目标与成功指标

| 目标 | 衡量指标 | 上线 3 个月目标值 |
| --- | --- | --- |
| 订单线上化 | 线上订单占比 | ≥ 60% |
| 回款加速 | 尾款平均回收天数 | 从 30 天降至 7 天内 |
| 服务可追溯 | 安装/维修工单留痕率 | 100%（含照片与签字） |
| 师傅效率 | 单师傅日均完成工单 | 提升 20% |
| 客户复购 | 12 个月内复购/转介绍率 | 提升 10 个百分点 |
| 数据准确 | 订单与收款对账差异 | 0 笔 |

### 1.4 名词解释

| 名词 | 含义 |
| --- | --- |
| SKU / 配置 | 同一机型下的可售组合，如"平缝机 A + 台板 + 伺服电机" |
| 定金 / 尾款 | 下单先付的部分（默认 30%）与安装验收后支付的余款 |
| 安装工单 | 由订单派生、派给安装师傅的服务任务 |
| 维修工单 | 由报修派生、派给维修师傅的服务任务 |
| 一机一码 | 每台售出设备绑定唯一机身码（SN），形成电子设备档案 |
| 保内 / 保外 | 在保修范围内免费维修；否则需报价并经客户确认 |
| 档期 | 师傅某天可承接的工单容量与已被占用的时段 |

### 1.5 项目范围

**本期做（MVP + P1）**：商品与配置、下单与定金/尾款、指定安装师傅、安装工单履约、报修与维修工单、客户 360、订单与账款看板、师傅端、库存、消息通知、基础报表、权限与审计。

**本期不做**：多商户入驻与分账、自建物流、直播带货、AI 故障诊断、供应链采购（进销存完整版）、旧机回收估价。这些列入演进路线（架构文档 §12），架构上预留扩展点。

## 二、可行性分析

### 2.1 技术可行性：成熟，无技术风险

所需能力全部是微信生态的标准能力，没有需要自研的底层技术：

| 能力 | 实现方式 | 成熟度 |
| --- | --- | --- |
| 微信登录 / 手机号 | `wx.login` + `code2session`，手机号快速验证组件 | 官方标准能力 |
| 在线支付 | 微信支付 APIv3 JSAPI（小程序内 `wx.requestPayment`） | 官方标准能力 |
| 消息触达 | 订阅消息（一次性/长期），模板需提前申请 | 官方标准能力 |
| 图片/视频留痕 | `wx.chooseMedia` + 对象存储直传 | 通用方案 |
| 地图与距离 | 腾讯位置服务（逆地址解析、距离计算） | 通用方案 |
| 电子发票 | 微信电子发票 / 第三方开票服务 | 可选，P2 |

后端采用 Java 单体（Spring Boot 3 + MySQL + Redis），是本项目量级的最优解：日订单量按 50–200 单估算，单机 2C4G 足够，无需微服务带来的运维复杂度。开发人员只需掌握 Spring Boot + MyBatis-Plus 即可维护，符合"我自己能看懂"的诉求。

**结论：技术可行，无卡点。**

### 2.2 合规可行性：有硬门槛，须提前办理

这是本项目**唯一可能延期**的环节，务必在开发启动前并行办理：

| 事项 | 要求 | 周期（参考） | 不办的后果 |
| --- | --- | --- | --- |
| 小程序主体认证 | 企业营业执照，认证费 300 元/年 | 1–3 个工作日 | 无法使用支付、无法上线 |
| 微信支付商户号 | 企业资质 + 对公账户，费率约 0.6% | 3–7 个工作日 | 无法在线收款 |
| 小程序类目 | 电商平台/商家自营（需对应资质） | 1–3 个工作日 | 审核驳回 |
| 域名与备案 | 已备案域名 + HTTPS 证书 | 备案 7–20 天 | 小程序无法请求接口 |
| 隐私合规 | 隐私政策、用户授权弹窗、最小必要采集 | 开发内置 | 审核驳回 / 下架风险 |
| 电子合同（可选） | 第三方 CA 或平台签 | 按需 | 大额交易举证弱 |

> **风险提示**：若支付资质尚未办妥，可先上线"线下收款登记"模式（后台手工登记定金/尾款，客户端只展示应付金额），支付能力作为开关后置开启。产品设计上已把"支付渠道"抽象为可配置项，不影响主流程。

### 2.3 经济可行性：投入可控，回报可算

**一次性投入（自研口径，按二线城市人力估算）**

| 项目 | 说明 | 估算 |
| --- | --- | --- |
| 后端开发 | 约 60 人日 | 3.0 万元 |
| 小程序前端 | 约 30 人日 | 1.8 万元 |
| 后台前端 | 约 25 人日 | 1.5 万元 |
| 设计 / 测试 / 项目管理 | 约 20 人日 | 1.2 万元 |
| 合计 | 约 135 人日 | **7.5 万元左右** |

**持续性投入**：服务器与云资源约 3,000–5,000 元/年；认证 300 元/年；支付手续费按流水 0.6%；短信按量。

**回报测算（以年销 300 台、客单 6,000 元、年营收 180 万元的门店为例）**

- 减少漏单/错单 3% → 约 5.4 万元营收；
- 尾款回收从 30 天缩短到 7 天，按年化资金成本 8% 估算 → 约 0.9 万元；
- 师傅调度效率提升 20%，同等人力多承接 15%–20% 工单 → 约 1–2 万元人工成本节约；
- 复购与转介绍提升带来的增量，按 5% 计 → 约 9 万元营收。

即使只兑现一半，**投入回收期在 6–10 个月**。若考虑"客户资产数字化"的长期价值，可行性更高。

### 2.4 运营可行性：真正的难点在人

系统本身不难，难的是让三类人愿意用：

| 角色 | 阻力 | 应对设计 |
| --- | --- | --- |
| 客户 | 习惯微信直接问价，不愿下载/注册 | 微信一键登录、无需注册；保留"电话/微信咨询"入口；下单只需 3 步 |
| 安装/维修师傅 | 嫌麻烦、不愿被"监控"、年纪偏大 | 师傅端只保留 4 个按钮（接单/导航/拍照/完成）；大字号；工单完成即结算可见；不与罚款强绑定，先做"记录"再做"考核" |
| 店员/店长 | 双系统重复录入 | 提供"后台代客下单"，线下成交也能进系统；Excel 客户与订单可批量导入 |

**结论：运营可行，但必须"先减负、后管控"**——第一版只做留痕和提醒，不做强考核，否则一线会抵触。

### 2.5 风险清单与对策

| 编号 | 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- | --- |
| R-01 | 支付资质未按时办妥 | 高 | 中 | 支付渠道做成开关，先线下登记；资质与开发并行启动 |

### 2.6 可行性结论

**技术上完全可行，商务上投入产出合理，合规上有明确的前置条件，运营上需要"渐进式推广"。** 建议立项，按"先交易、后服务、再经营"的顺序分三期交付（见 §11）。

## 四、业务流程

### 4.1 全流程概览

一条订单从"看机器"到"装好收钱"，中间要跨越四个角色、两次收款、一次派工。整体链路如下：

![图 1　功能地图：三类角色、六个功能域](diagrams/fig1-functional-map.png)

**主链路**：客户选购 → 下单（选师傅）→ 付定金 → 系统派工 → 师傅接单上门 → 安装调试 → 客户验收 → 付尾款 → 完成/评价。
**服务链路**：客户报修 → 保修判定 → 选/派维修师傅 → 上门检测报价 → 客户确认 → 维修 → 确认评价 → 归档到设备档案。

### 4.2 下单与定金支付

![图 2　客户下单与定金支付流程](diagrams/fig2-order-flow.png)

几个关键设计点：

1. **先选师傅，再付定金**。客户在提交订单时就能看到师傅的评分、距离、擅长机型和最近可预约日期，避免"付了钱不知道谁来装"。若客户不指定，系统按规则自动派单。
2. **库存与档期双重校验**。下单时校验 SKU 库存与师傅档期，任一不满足即给出替代方案（改期/改派/候补），而不是让客户付完钱再告知。
3. **定金支付成功才生成安装工单**。未支付的订单不占用师傅档期，30 分钟未支付自动关闭并释放库存与档期。
4. **支付回调是唯一可信来源**。前端"支付成功"的回调只用于跳转，订单状态以微信支付异步通知为准，并配主动查单兜底（见架构文档 §4.4）。

### 4.3 安装履约与尾款

![图 3　安装履约与尾款收取流程](diagrams/fig3-install-flow.png)

履约环节是整个方案里"最值钱"的部分，因为它把过去只存在于电话和口头承诺里的服务过程变成了可追溯的记录：

- 师傅接单后必须确认上门时间，改约需客户同意，拒单自动改派；
- 上门需**定位打卡**，安装过程可拍照（拆箱、组装、调平、试缝成品）；
- 安装单必须填写机身码（形成电子设备档案）、上传现场照片、客户**电子签字**；
- 客户在小程序点击"确认验收"后，系统才生成尾款单——**验收是尾款的触发器**，避免"装完就催钱"的尴尬；
- 验收不通过进入返工/换机流程，由商家介入，尾款不生成。

### 4.4 订单状态机

![图 4　订单状态与异常分支](diagrams/fig4-order-state.png)

状态机是订单模块的核心约束。**所有状态变更必须经过状态机校验**，禁止在业务代码里直接 `update status = ?`，否则后期一定会出现"已取消的订单又被支付回调改成已付款"这类脏数据（架构文档 §4.3 给出实现）。

### 4.5 报修与维修

![图 5　报修与维修流程](diagrams/fig5-repair-flow.png)

维修流程与销售流程最大的不同是**费用不确定**：同一个"跳线"可能是针杆问题（几十元），也可能是旋梭磨损（几百元）。因此设计上把"检测"和"施工"拆成两个阶段，中间插一个"客户确认报价"的卡点：

- 保内：系统按保修规则自动判定，免费维修，费用计入厂商/商家成本；
- 保外：先收检测费/上门费（可配置），检测后出报价单，客户线上确认才可施工；
- 换件必须登记新件与旧件去向（旧件归客户还是回收），这是纠纷高发点；
- 维修完成后写入设备档案，形成"这台机器的一生"。

### 4.6 异常场景处理

| 场景 | 触发条件 | 系统处理 | 人工介入 |
| --- | --- | --- | --- |
| 支付超时 | 下单 30 分钟未支付 | 自动关闭订单，释放库存与档期，推送提醒 | 无 |
| 库存不足 | 下单/支付时校验失败 | 拦截下单，推荐同价位替代机型或到货通知 | 客服跟进 |
| 档期冲突 | 所选时段已被占用 | 置灰不可选，推荐相邻日期/其他师傅 | 无 |
| 师傅拒单 | 接单前拒绝或 30 分钟未响应 | 自动改派（最多 3 次），仍失败转人工 | 店长指派 |
| 师傅爽约 | 超过预约时间 2 小时未打卡 | 标记异常，通知店长，可改派并记录绩效 | 店长处理 |
| 验收不通过 | 客户点"不通过"并填原因 | 工单转返工，尾款不生成，商家介入 | 店长处理 |
| 尾款逾期 | 生成后 7 天未付 | 自动催付（第 1/3/7 天），15 天限制再次下单 | 客服催收 |
| 退款申请 | 已付定金后申请退款 | 进入审批流，店长审批后原路退回 | 店长审批 |
| 保外拒修 | 客户不确认报价 | 工单关闭，收取检测费（若已上门） | 无 |
| 维修返修 | 同一设备 30 天内同故障再报 | 自动标记"返修"，免收上门费，计入师傅质量 | 店长复盘 |

### 5.4 商家后台（模块 F）

#### 5.4.1 客户 360（核心需求）

商家最想要的是"一个客户点进去，什么都能看到"。客户详情页按以下结构组织：

| 区块 | 内容 | 用途 |

### 5.5 增值功能建议（P2，按需取舍）

这些不是必做，但都是这个行业真实存在的增收点，建议在架构上留好口子：

1. **以旧换新 / 二手机回收**：客户提交旧机信息 → 估价 → 抵扣新机款；
2. **保养套餐**：缝纫机需要定期清洁、加油、换针、调梭，可卖年费保养卡（4 次/年），是稳定的服务收入；
3. **配件耗材商城**：机针、旋梭、压脚、油、皮带——高频低价，拉复购；
4. **转介绍奖励**：老客户推荐新客户成交，双方得优惠券；
5. **培训课程**：新机操作培训、特种机工艺课，线上报名 + 线下开课；
6. **电子质保卡**：扫码即见保修状态，替代纸质保修卡；
7. **赊销与信用额度**：给服装厂客户设额度与账期，超限停单；
8. **多门店/多网点**：乡镇网点代销、库存共享、业绩归属。

## 六、业务规则汇总

| 编号 | 规则 | 说明 |
| --- | --- | --- |
| BR-01 | 定金比例 | 默认 30%，范围 10%–100%，可按机型/客户等级配置 |
| BR-02 | 尾款金额 | 尾款 = 订单应付总额 − 已付定金 − 已核销优惠；以分为单位计算，禁止浮点 |
| BR-03 | 尾款触发 | 客户确认验收后生成；7 天内自动催付（第 1/3/7 天）；逾期 15 天限制再次下单 |
| BR-04 | 库存占用 | 下单锁定 30 分钟，支付成功转为实扣，取消/超时释放 |
| BR-05 | 派单顺序 | 客户指定 > 距离 + 技能 + 评分 + 负载综合评分；30 分钟未接自动改派，最多 3 次 |
| BR-06 | 档期容量 | 每位师傅每日默认 3 单，可按人配置；已被占用时段不可重复预约 |
| BR-07 | 保修起算 | 以安装完成日（无安装则以签收日）起算；整机 12 个月、电机电控 24 个月，可按机型配置 |
| BR-08 | 保外报价 | 报价 = 工时费 + 配件费 + 上门费；> 300 元须客户线上确认后方可施工 |
| BR-09 | 退款规则 | 未支付可自助取消；已付定金退款需审批，可配置手续费比例 |
| BR-10 | 评价规则 | 订单完成后 7 天内可评；师傅评分 = 近 90 天评价加权平均（近期权重更高） |
| BR-11 | 数据权限 | 师傅仅见自己工单；客服可见全量但不可改价；改价/退款/删除需店长及以上 |
| BR-12 | 客户合并 | 同一手机号视为同一客户，历史订单与设备自动归并 |
| BR-13 | 金额精度 | 数据库以"分"（bigint）存储，前端展示保留两位小数 |
| BR-14 | 操作留痕 | 订单状态、金额、指派人三项变更必须写操作日志（操作人、时间、前后值） |

## 九、界面与视觉规范（红白配色）

### 9.1 色彩体系

整体走"白底 + 红点缀"的路线：白色承担 60% 以上的面积保证清爽，浅灰承担信息分层，红色只用于**行动点与强调**——大面积铺红会让工业品显得廉价，也会让价格信息难以阅读。

| 角色 | 色值 | 用法 |
| --- | --- | --- |
| 主色（品牌红） | `#C8102E` | 主按钮、价格、选中态、重要标签、进度节点 |
| 深红 | `#96061F` | 按钮按下态、深色标题、红底上的描边 |
| 浅红底 | `#FFF5F6` | 卡片高亮、提示条背景、师傅卡片选中 |
| 红色描边 | `#F0BEC6` | 浅红底上的 1px 边框 |
| 主文字 | `#1A1E24` | 标题与正文 |
| 次要文字 | `#6C7480` | 说明、时间、辅助信息 |
| 分割线 | `#E5E8ED` | 列表分隔、卡片描边 |
| 页面底色 | `#F7F8FA` | 页面背景，让白卡片浮起来 |
| 成功/警告 | `#0F7B57` / `#B45309` | **仅用于状态标识**，不用于装饰 |

## 十、验收标准

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 客户下单并付定金 | 30 秒内完成；支付成功后订单转"待安装"且生成工单；重复回调不产生重复工单 |
| AC-02 | 客户指定师傅 | 只能选有档期且技能匹配的师傅；无档期时置灰并给出建议 |
| AC-03 | 师傅完成安装 | 上传 3 张照片 + 机身码 + 客户签字后方可提交；提交后客户收到验收通知 |
| AC-04 | 客户验收并付尾款 | 尾款金额 = 总额 − 定金，误差为 0；支付后订单置为已完成 |
| AC-05 | 尾款逾期 | 第 7 天自动催付；第 15 天该客户无法再次下单并提示原因 |
| AC-06 | 客户报修 | 保内自动判免费；保外生成报价单，未确认不能进入"维修中" |
| AC-07 | 商家查看客户 360 | 打开客户详情 2 秒内展示订单、设备、待付金额、偏好标签 |
| AC-08 | 账款核对 | 订单已付 + 待付 = 应付总额；收款流水合计与已付一致 |
| AC-09 | 权限隔离 | 师傅 A 无法通过改 URL 查看师傅 B 的工单（返回 403） |
| AC-10 | 异常恢复 | 模拟支付回调丢失，5 分钟内由主动查单补偿为已支付 |
| AC-11 | 数据导出 | 订单导出 Excel 字段完整、金额与页面一致 |
| AC-12 | 视觉一致性 | 主色仅使用 `#C8102E`；按钮、价格、标签符合 §9 规范 |

## 十二、待确认问题

以下问题会显著影响设计，建议在开发启动前确认：

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| Q-01 | 是否只有一家店，还是有多门店/多经销商？ | 决定是否引入 `tenant_id` / `store_id` 与数据权限模型（当前按单店设计、预留多租户） |
| Q-02 | 支付主体是否已具备企业资质与商户号？ | 决定支付能否在 MVP 上线 |
| Q-03 | 师傅是自有员工还是外包？ | 决定结算、提成、发票与权限模型 |
| Q-04 | 是否存在赊销/账期客户？比例多大？ | 决定信用额度与账龄模块的优先级 |
| Q-05 | 是否已有进销存/ERP/财务系统？ | 决定是否需要对接与双向同步 |
| Q-06 | 历史订单与客户数据以什么形式存在？ | 决定导入工具的工作量 |
| Q-07 | 是否需要电子合同/电子签章？ | 大额交易举证，涉及第三方服务与费用 |
| Q-08 | 是否需要以旧换新与二手机业务？ | 影响 SKU 模型（需支持非标品） |
